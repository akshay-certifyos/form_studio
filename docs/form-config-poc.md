# Config-Driven Form Authoring — POC

**Status:** Design — pre-implementation
**Scope:** v0 proof of concept
**Stack:** Quarkus 3 (Java 21), MongoDB, Domain-Driven Design

---

## 1. Purpose & Scope

This POC evaluates whether payer credentialing forms can be **defined as configuration** — composed from a reusable question catalog — instead of hand-authored JSON blobs interpreted by bespoke frontend code.

It doubles as a proposal for rewriting the service under a **Domain-Driven Design** paradigm on Mongo, ahead of the DAL migration.

### In scope for v0

| Area | Included |
|---|---|
| Question catalog | Questions, option sets, validation rules, platform mappings |
| Sections | Section templates (reusable), section definitions (tenant) |
| Forms | Form blueprints (reusable), form definitions (tenant) |
| Compilation | Definition → immutable compiled artifact |
| Publishing | Versioning, change classification, freeze semantics |
| Expressions | Grammar, parser, **compile-time validation only** |

### Explicitly out of scope for v0

- **Response capture** — applications, answers, autosave, submit
- **Runtime expression evaluation** — belongs to the rendering engine and to response capture
- **Submission integration** — the existing `submissionActions` pipeline is untouched
- **Attestation** — unaffected
- **PDF ingestion** — parked; design retained in §11
- **Authoring UI** — definitions are authored as YAML/JSON in a repo for v0
- **Placement-scoped answer keys at runtime** — v0 compiles to the *existing* answer shape; the model is placement-scoped (§5.6, §10)

## 2. Problem Statement

### The backend is schema-agnostic today

`FormVersion.schema` is an opaque `JsonNode`. `FormTemplateService.getFormConfig` fetches the active version and passes the blob straight to the frontend. **Nothing in the backend parses pages, sections, response types, validations, conditional visibility, or hard stops.**

Every P0 form behaviour in the Provider Portal PRD §4 — page/section layout, response types, input validations (NPI checksum, TIN 9-digit, phone format), conditional visibility, conditional question logic, conditional select filtering, hard-stop logic, error counts, preview screen — is implemented as **frontend code**.

### The consequences

**1. Business rules are code, so config changes need releases.**
CP-38192 is the clearest example. A payer rule — *"hide the DEA Registration section when specialty is one of DC, OD, PhD, Pathologist, Radiologist"* — is a sentence a credentialing analyst could write. Today it requires a rendering-engine change, a Jira story, and a release. Two client forms (NSCP, Florida Blue) are blocked on it, and three Florida Blue sections currently ship unconditioned (always visible), which is functionally wrong.

The root cause is that `condition` is **flat and non-recursive**: exactly one `{field, operator, value}`, one level deep.

**2. Forms are authored as opaque generated blobs.**
A schema is generated by a skill, the JSON is taken, and it is uploaded. There is no diffable, reviewable, composable intermediate representation — and no reuse between payer forms that are 70–80% identical in substance.

**3. Destructive publishing is gated on a checkbox.**
`FormVersion.isTextOnlyUpdate` is a human-asserted boolean. When false, `publishDraft` resets **every in-progress application** for that template — repointing `formVersionId` and wiping `answers` and `stepProgress` to empty objects, with individual failures logged and swallowed. A person's judgement call decides whether providers lose their work.

**4. Downstream mappings are fragile.**
`submissionActions.fieldMappings` uses string paths keyed on **section display labels**: `"degree": "answers.Degree Details.credentialingDegree"`. Rename the section and the mapping silently resolves to null — no error, the provider record is just quietly missing a field. These are hand-written per tenant, per form.

**5. Client-only enforcement is not enforcement.**
The API accepts whatever `answers` blob arrives. Hard stops are applied by the frontend sending `status: "ineligibletocomplete"` on a plain `PUT`. Validation and disqualification rules that only the client performs are advisory.

### Additional context

Most payers already have an existing PDF form that Certify digitises. That workflow is a first-class use case, not an afterthought — see §11.

## 3. Design Principles

These five rules generate every decision in this document. They are recorded with rationale so they are not re-litigated.

### P1 — Tree for structure, recursive expressions for logic. Not a graph.

Two different things get called "relationships":

- **Composition** — a form contains ordered section placements, each containing questions. Strictly a **tree**, no cycles by construction.
- **Logic** — an answer affects visibility, options, or hard stops. This is not an edge between nodes; it is **an expression attached to a node that references other nodes**.

Modelling logic as typed graph edges (`SHOWS`, `HIDES`, `FILTERS_OPTIONS`, `TRIGGERS_HARDSTOP`, …) means every new capability is a new edge type, a migration, traversal code, and UI. That is the rule-engine problem relocated from the frontend into the database.

A **recursive expression** solves AND / OR / NOT / nesting permanently, with an operator table instead of operator code.

**Why no graph is needed at all.** Cycle detection, dangling-reference detection, impact analysis, and unreachable-section detection are all *the same single pass* over the compiled tree, building a transient reverse-reference map. That map is a local variable, not infrastructure. A persistent dependency graph is what you need **when you do not have a compile step** — compilation collapses the need, because at compile time the whole resolved tree is in memory and afterwards the artifact is frozen.

The one genuinely cross-cutting query — *"which forms across all tenants use this question or option set?"* — is a table written at compile time (`form_question_usage`), answered with a join.

### P2 — Compile, don't interpret.

The authoring model is a **compiler** whose output is the existing runtime artifact.

```
catalog + templates + definition  ──compile──▶  form_versions.schema (unchanged)
         (new: authoring)                            (existing: runtime)
```

Consequences:
- The rendering engine does not learn the catalog exists.
- `getFormConfig` does not change. The submission pipeline does not change. Existing forms keep working.
- Cross-reference validation (cycles, dangling refs, unreachable sections, orphans) happens **before publish**, not at 2am in a submission pipeline.
- Change classification becomes a **diff of two compiled artifacts**, retiring the `isTextOnlyUpdate` checkbox.

#### Amendment — the condition slot is not backward compatible, and the POC does not pretend otherwise

The bullets above are true of **structure** and false of **conditions**. Recorded here because the
original wording ("existing forms keep working", "zero rendering-engine changes") was too strong, and
because the reason is inherent rather than a gap in the build.

Today's renderer (`DynamicFormRenderer.tsx`) defines:

```ts
interface StepCondition { field: string; operator: 'equals' | 'notEquals' | 'contains'; value: any }
```

Three operators, one level deep, and the key is `operator`. The POC emits the grammar's own JSON —
key `op`, twelve operators, recursive. **A recursive `all`/`any`/`not` cannot be represented in one
flat triple**, so no naming scheme could have reconciled the two: the incompatibility is the very
thing CP-38192 is about.

The naming difference (`op`/`eq`/`nin` versus `operator`/`equals`) is deliberately left as-is. This
is a POC; renaming would imply compatibility that the recursion already rules out, and the shared
grammar has one spelling on both sides of the FE↔BE conformance suite. If this were productionised,
the compiler would gain a lowering step that emits production's flat form for the rules that fit it
and the recursive form only for the rules that don't.

**The failure mode matters more than the naming.** `evaluateCondition` ends with `default: return
true`, so an unrecognised operator makes the step **visible**. A POC artifact fed to today's renderer
would not error — every conditional step would silently become permanent. For Florida Blue that means
the DEA section showing for chiropractors, i.e. the exact defect this design exists to remove.

**This is already happening in production, without the POC.** Of the two real payer configs imported
for the round-trip gate, Premera contains three conditions today's renderer cannot evaluate:

| Field | Condition | Actual behaviour |
| --- | --- | --- |
| `providerNetworkAssociateName` | `{operator: "all", conditions: [...]}` | always visible |
| `accreditationCertificateUpload` | `{operator: "notEmpty"}` | always visible |
| `nonAccreditedSurveyUpload` | `{operator: "equals", value: ""}` against a multi-select | **never** visible |

The third is the serious one: a non-accredited facility is never asked for its State or Medicare
survey, because an unselected multi-select is not `""`. The `visibilityCondition` keys sitting beside
those conditions are read by nothing at all, and CalMHSA's `_metadata.notes` asks a future
implementer to "implement `operator` `all` with a `conditions` array, and `notEmpty` on select
values" — authors are already writing rules the renderer cannot run, and shipping them.

So the honest framing of P2 is: **the compiler removes the need to change the renderer for
structure, and makes explicit a renderer change that conditions already needed.** That change is
bounded — replace `evaluateCondition` with the shared evaluator, one function, already covered by 85
conformance cases on both sides — not a rewrite of a 3,991-line file.

### P3 — Content is referenced; structure is copied. Compile is the freeze point.

| Boundary | Rule |
|---|---|
| Global template/blueprint → tenant definition | **Copy-on-use**, with `sourceTemplateId` + `sourceTemplateVersion` provenance |
| Within the tenant's authoring layer | **Live reference** (`form_definition → section_definition → catalog question`) |
| Publish | **Freeze** — resolves every live reference into the immutable artifact |

Certify editing a global template never mutates a tenant's form. A tenant editing a shared section affects their own forms only on next publish. A published version is never affected by anything.

This matters for compliance: you must be able to reproduce exactly what a provider saw and signed.

### P4 — Closed vocabularies, not code.

Operators, validation rules, and response types are **enumerated registries with parameters**, each implemented once. Adding a payer rule means adding config, not a branch.

- Operators: `eq, neq, in, nin, gt, gte, lt, lte, exists, empty, matches`
- Validation rules: `required, minLength, maxLength, length, numeric, phone, fax, tin, npiChecksum, email, dateRange, regex, fileType, fileSize`
- Response types: `text, textGroup, date, singleSelect, multiSelect, buttonSelect, file, group`

Conditional select filtering is expressed by **tagging option values**, never by hardcoding parent-child rules.

### P5 — Normalize where there is sharing; embed where there is not.

Sections are the smallest independently reusable unit, so they get their own collection. A **question instance** belongs to exactly one section and is never shared — normalising it buys nothing and costs ordering and atomicity. Instances are embedded in the section.

The cost of normalisation is zero at runtime: **nothing reads these collections on the request path.** Only the compiler does, on publish.

---

### P6 — One condition grammar, many attachment points.

Visibility is not the only rule a form needs. Requiredness, defaults, option filtering, cross-field validation and viewer-gating are all "when X, do Y". If each arrives as its own bespoke mechanism, authoring returns to engineers and tickets — the exact problem this project exists to remove, reached by a different route.

**There is one expression grammar. It attaches in many places.** v0 implements only `visibleWhen`, but every attachment point is named and reserved in the schema from day one.

| Attachment point | Attaches to | v0 |
|---|---|---|
| `visibleWhen` | section placement, question instance | **implemented** |
| `requiredWhen` | question instance | reserved |
| `defaultWhen` | question instance | reserved |
| `optionWhen` | option value | reserved |
| `validWhen` | question instance | reserved |
| `audienceWhen` | section placement | reserved |

This costs a field name now and is close to unrecoverable if visibility-only ships first.

## 4. Domain Model

### 4.1 Domain types

| Type | Contexts | Rationale |
|---|---|---|
| **Core** | `question_catalog`, `form_authoring` | Speed-to-onboard a new payer form *is* the business capability |
| **Supporting** | `form_response`, `submission_integration`, `form_ingestion` | Necessary, not differentiating |
| **Generic** | Identity, document storage, notification, audit | Reuse; already solved |

`question_catalog` is the asset that compounds. Without it, `form_authoring` is a commodity form builder.

### 4.2 Bounded contexts

Boundaries were drawn using the **language test**: does the same word mean genuinely different things?

#### `question_catalog` — core, **in v0**

The library of reusable question types, option sets, validation rules, and platform mappings. Certify-owned, cross-tenant, slow-changing, stewarded.

- **Aggregate roots:** `Question`, `OptionSet`
- **Invariant:** no two active entries mean the same thing
- **Passes the language test:** *Question* here is a reusable **type**; in `form_authoring` it is an **instance**. Different concept, different owner, different cadence.

#### `form_authoring` — core, **in v0**

Composes catalog questions into sections, sections into forms, and compiles definitions into immutable published versions.

- **Aggregate roots:** `SectionDefinition`, `FormDefinition`, `FormVersion`
- **Invariants:** composability (definitions) and immutability (versions)

**Publishing is an aggregate inside this context, not a separate context.** It fails the language test — *Form Definition* means the same thing on both sides, no term is contested, same team, same deployment. Different invariants and cadence are what **aggregates** express; promoting them to contexts buys ceremony and returns nothing.

Extraction stays cheap if ever warranted: `FormCompiler` is a pure function over `(definition, catalogSnapshot)` and `FormVersion` is already its own aggregate.

#### Deferred contexts

| Context | Status |
|---|---|
| `form_response` | Out of v0. Owns `Application`, `Answer`, submit, hard-stop state |
| `submission_integration` | Out of v0. Existing `submissionActions` pipeline, unchanged |
| `form_ingestion` | Parked. PDF → extraction → matching → blueprint diff (§11) |

### 4.3 Context map

```
question_catalog ──── supplier ────▶ form_authoring
        │                                   │
        │ published language                │  FormVersionPublished
        │ (platform mappings)               │  { changeClass, changedKeys }
        ▼                                   ▼
submission_integration  ◀───────────  form_response
       (deferred)                       (deferred)
```

Two relationships stated precisely:

**The condition expression grammar is a Published Language, not a context.** It has no independent lifecycle or actor. It is consumed by `form_authoring` (stores and validates it) and by the rendering engine (evaluates it). Because the frontend must evaluate it for instant reveal, it has **two implementations** — so the **conformance suite is the contract**, not shared code.

**`form_authoring` → `form_response` is an event, not a call.** Publishing states what happened; response capture decides what "reset" means for its own aggregates. The most dangerous operation in the system stays behind a boundary. In v0 the event is emitted with no subscriber.

### 4.4 Ubiquitous language

**`question_catalog`** — Question, Response Type, Option Set, Option, Tag, Alias, Validation Rule, Platform Mapping, Steward, Promotion, Duplicate, `proposed → active → deprecated`

**`form_authoring`** — Question Instance, Instance Key, Section Definition, Section Template, Form Definition, Form Blueprint, Placement, Origin (`template` | `added`), Enabled, External Ref, Drift, Override, Compile, Compiled Form, Form Version, Publish, Change Class, Changed Keys, Definition Snapshot

### 4.5 Naming collisions — notes only

The POC has naming freedom. These are recorded so they are handled deliberately if this becomes production.

| Existing term | Collision |
|---|---|
| `FormTemplate` | Currently the tenant's container record; here *template* means a reusable blueprint. Direct collision. |
| `schema` | Currently the compiled artifact; collides with Mongo schema and JSON Schema. This doc uses **Compiled Form**. |
| `draft` | Means both an unpublished version and an in-progress application. |
| `field` | Used for questions today. Here **Question** is the unit; **Field** means a sub-part of a grouped question (Address → line1). |
| `version` as `1.0 → 10` | Scaled-integer encoding leaked into a domain concept. Here Version is a plain integer sequence; display formatting is presentation. |
| `status` | One word doing four jobs across Form, Version, Application, Entity. Named per aggregate here. |

## 5. Data Model (MongoDB)

### 5.1 `option_sets`

Values are catalogued separately from response type (the widget). Conditional filtering is driven by **tags**, never hardcoded rules.

```json
{
  "_id": "os_specialties",
  "tenantId": null,
  "key": "specialties",
  "name": "Specialties",
  "status": "active",
  "options": [
    { "value": "cardiology",   "label": "Cardiology",
      "tags": { "providerType": ["MD", "DO"] } },
    { "value": "chiropractic", "label": "Chiropractic",
      "tags": { "providerType": ["DC"] } }
  ],
  "createdBy": "system", "updatedBy": "system",
  "createdAt": "ISODate", "updatedAt": "ISODate"
}
```

`tenantId: null` = Certify-global. A set value makes it tenant-owned.

### 5.2 `question_catalog`

```json
{
  "_id": "q_npi",
  "tenantId": null,
  "key": "npi",
  "label": "National Provider Identifier (NPI)",
  "helpText": "Your 10-digit individual NPI",
  "responseType": "text",
  "categoryKey": "identity",
  "optionSetKey": null,
  "children": null,
  "validations": [
    { "rule": "length", "exact": 10 },
    { "rule": "npiChecksum" }
  ],
  "platformMapping": { "practitioner": "npi", "facility": "npi" },
  "aliases": ["NPI", "NPI Number", "National Provider ID"],
  "tags": ["identity"],
  "status": "active",
  "createdBy": "...", "updatedBy": "...",
  "createdAt": "ISODate", "updatedAt": "ISODate"
}
```

Three fields doing significant work:

- **`platformMapping`** — defined once globally. This is what collapses N tenants × M forms of hand-written `fieldMappings` string paths into one table.
- **`aliases`** — improves matching, and is where payer-specific phrasings are parked **instead of minting near-duplicate catalog entries**.
- **`categoryKey`** — required, and a key into `question_categories` rather than a label. See §5.2a.

### 5.2a `question_categories`

```json
{ "_id": "identity", "label": "Identity & identifiers",
  "description": "Who the provider is, and the numbers that identify them across systems.",
  "order": 10 }
```

**Every question belongs to exactly one category, and the reference is required.** Without it a
catalog is a flat alphabetical list, which works at 34 entries and fails at 300 in a specific way:
picking from a flat list requires already knowing what you are looking for, so an author adds the
questions they remember and never discovers the rest — which is how a shared catalog stops being
shared.

**Stored, not an enum.** Both are closed vocabularies, and P4 asks for closed vocabularies *not
expressed as code* — an enum would mean a release to add "Behavioral health", which is the cost this
design exists to remove. This is the `option_sets` pattern: you cannot invent a category by typing,
and you can add one by configuring.

**A category is intrinsic to the question, never to where it is used.** "Do you have a CAQH ID?" sits
in Identity & identifiers even though the Florida Blue form asks it inside Billing Setup: the section
decides placement, the category decides the shelf. Conflating them would give one question a different
category per form, at which point the taxonomy carries no information.

**Global, never per tenant.** A taxonomy that varies by tenant cannot group a shared catalog — the
value of browsing by category is that every tenant sees the same shelves.

`order` is explicit rather than alphabetical, because the useful sequence follows how a credentialing
file is assembled: identity first, attestation last. Alphabetical would open with Attestation, which
is the last thing anyone fills in.

Referential integrity is enforced where a reference is made, not in the record — an aggregate cannot
see a repository — and by `CategoryFixtureTest`, which also asserts no category is empty. That last
one is a rule about the fixtures rather than the model: a taxonomy invented ahead of its content is a
guess, and this design's whole argument is that shapes get promoted from real use.

The key is the document id. Unlike questions and option sets there is no surrogate id, because a
category has no identity apart from its key, and a second one would be another thing to keep in step
for no gain.

Grouped inputs (PRD §2.4 — per-field required-ness within a group):

```json
{
  "_id": "q_address",
  "key": "address",
  "responseType": "textGroup",
  "children": [
    { "key": "line1", "label": "Address Line 1", "responseType": "text" },
    { "key": "state", "label": "State", "responseType": "singleSelect",
      "optionSetKey": "us_states" },
    { "key": "zip",   "label": "ZIP", "responseType": "text",
      "validations": [{ "rule": "regex", "pattern": "^\\d{5}(-\\d{4})?$" }] }
  ]
}
```

### 5.3 `section_templates`

Global or tenant-scoped reusable blueprints. Copy-on-use.

```json
{
  "_id": "st_licensure",
  "tenantId": null,
  "key": "licensure",
  "name": "Licensure",
  "version": 3,
  "intro": "List all active state licenses.",
  "repeating": { "enabled": true, "minItems": 1, "maxItems": 20,
                 "itemLabel": "License" },
  "questions": [
    { "key": "licenseState",      "catalogQuestionId": "q_license_state",  "order": 10 },
    { "key": "licenseNumber",     "catalogQuestionId": "q_license_number", "order": 20 },
    { "key": "licenseExpiration", "catalogQuestionId": "q_license_exp",    "order": 30 }
  ],
  "status": "active"
}
```

### 5.4 `section_definitions`

Tenant-scoped, reusable across that tenant's forms. Owns **intrinsic content only**.

```json
{
  "_id": "sd_licensure_abc",
  "tenantId": "tenant_abc",
  "key": "licensure",
  "name": "Licensure",
  "intro": "List all active state licenses.",
  "repeating": { "enabled": true, "minItems": 1, "maxItems": 20,
                 "itemLabel": "License" },
  "sourceTemplateId": "st_licensure",
  "sourceTemplateVersion": 3,
  "externalRefs": ["providerType"],
  "questions": [
    { "key": "licenseState", "catalogQuestionId": "q_license_state",
      "origin": "template", "enabled": true, "order": 10, "required": true,
      "labelOverride": null,
      "visibleWhen": null, "requiredWhen": null, "defaultWhen": null, "validWhen": null },
    { "key": "licenseIssuer", "catalogQuestionId": "q_license_issuer",
      "origin": "added", "enabled": true, "order": 25, "required": false }
  ],
  "status": "active"
}
```

Question instances carry the reserved attachment points from §3 P6. Only `visibleWhen` is evaluated in v0; the rest exist so the next four kinds of rule are config rather than code.

**`externalRefs` is computed, not authored.** It is the section's contract — like a function signature. Placing this section in a form that has no `providerType` question fails at compile time with a clear message, rather than silently never rendering.

**`origin`** distinguishes template-inherited from locally-added questions, which is what makes drift computable.

**Disable, don't delete**, for `origin: "template"` questions — it preserves provenance so a template upgrade knows what to reconcile.

Three concepts that are easy to conflate:

| | Meaning | Effect on compiled artifact |
|---|---|---|
| `enabled: false` | Authoring-time exclusion | Compiled out entirely — never exists |
| `condition` | Runtime visibility | Present; shown/hidden per answers |
| deletion | Removes the row | Loses template provenance |

### 5.6 `form_definitions`

Tenant-scoped. Owns **placement**, not content.

```json
{
  "_id": "fd_nscp_practitioner",
  "tenantId": "tenant_abc",
  "formTemplateId": "ft_existing_id",
  "name": "NSCP Practitioner Application",
  "entityType": "practitioner",
  "status": "draft",
  "sourceBlueprintId": "fb_practitioner_recred",
  "sourceBlueprintVersion": 2,

  "namedConditions": {
    "specialtyExempt": {
      "label": "Specialty exempt from DEA requirements",
      "expr": { "field": "applicantDetails.specialty", "op": "in",
                "value": ["DC", "OD", "PhD", "Pathologist", "Radiologist"] }
    }
  },

  "placements": [
    { "placementKey": "practiceLocation",
      "sectionDefinitionId": "sd_address_abc",
      "order": 10, "enabled": true, "titleOverride": "Practice Location",
      "group": "Practice Information",
      "repeating": { "min": 1, "max": 10, "itemLabel": "Location" },
      "visibleWhen": null
    },
    { "placementKey": "billingAddress",
      "sectionDefinitionId": "sd_address_abc",
      "order": 20, "enabled": true, "titleOverride": "Billing Address",
      "group": "Billing",
      "visibleWhen": {
        "all": [
          { "field": "billingSetup.hasCaqhId",            "op": "eq", "value": "Yes" },
          { "field": "billingSetup.billingSameAsPrimary", "op": "eq", "value": "No"  }
        ]
      }
    },
    { "placementKey": "deaRegistration",
      "sectionDefinitionId": "sd_dea_abc",
      "order": 30, "enabled": true,
      "group": "Credentials",
      "visibleWhen": { "not": { "ref": "specialtyExempt" } }
    }
  ],

  "hardStops": [
    { "key": "noActiveLicense",
      "visibleWhen": { "field": "licensure.hasActiveLicense", "op": "eq", "value": "No" },
      "message": "An active state license is required to proceed.",
      "evaluateOn": "next" }
  ]
}
```

**`placementKey` is the answer namespace.** It is the addition the design review surfaced, and it is structural rather than cosmetic. Note the two placements above — `billingAddress` and `practiceLocation` — both compose the catalog's address questions from the same section definition. Their answers are `billingAddress.line1` and `practiceLocation.line1`: independent slots. Keyed by question alone they would be one slot, and the later write would silently destroy the earlier one. Four addresses on a real form (practice, billing, remit-to, mailing) turns that from a latent bug into a guaranteed one.

`placementKey` is author-supplied, unique within the form, and immutable once published — a change to it is classified `structural` by the diff.

**Cross-section conditions live on the placement, not the section definition.** The form level is the only place that knows the complete namespace, and it is what keeps section definitions genuinely reusable across forms.

**One grouping level: placements are steps.** *(Decision — closes §13 Q6.)* The target `FormConfig` has exactly one grouping level (`steps`), so this design has one too: a form is a flat ordered list of placements, and **each placement compiles 1:1 to a step**. A placement's `visibleWhen` maps directly onto the step's `condition` with nothing lost.

The alternative — a page level above sections — was rejected. Pages carried no behaviour (no conditions in practice, no reuse, no identity beyond a title), the live portal's section nav is flat, and making a page a step would force every section condition to be copied down onto each of its individual fields: lossy, and it makes the round-trip diff meaningless.

`group` survives as an **optional presentational label** on a placement. It compiles to nothing. If grouping ever needs behaviour — save points, completion gating, per-group progress — it gets promoted to a real level then, with a use case to justify it.

Both CP-38192 cases appear above as pure config: the NSCP compound-AND section and the Florida Blue `in` section. Neither requires code.

`formTemplateId` links to the **existing** `FormTemplate` record. `submissionActions` stays exactly where it is.

## 6. Condition Expression Language

One recursive grammar with many attachment points (§3, P6). The same node type expresses section visibility, question visibility, hard stops, option filtering and — when they land — requiredness, defaults and validation.

### Evaluation context

Expressions do **not** evaluate against answers alone. Production already gates steps by viewer role (`FormConfig.audience`), which is not an answer. The evaluator therefore takes a **context**:

```
context := {
  answers:  { <placementKey>.<questionKey>: value, ... },
  viewer:   { role: "admin" | "practitioner" },
  entity:   { ...portal_entity profile },
  tenant:   { ...tenant configuration }
}
```

A bare `field` reference resolves against `answers`. Other namespaces are addressed explicitly (`viewer.role`, `entity.npi`). Deciding this now costs a field name; retrofitting it means rewriting every stored expression.

**`viewer`, `entity` and `tenant` are therefore reserved and cannot be step keys.** A two-segment path is always an answer, so a step named `viewer` would make `viewer.role` ambiguous. Rejected by `StepKey` at construction rather than caught later by the compiler, since a step key is immutable once published.

### Grammar

```
expr := { "all":   [expr, ...] }                      // boolean AND over expressions
      | { "any":   [expr, ...] }                      // boolean OR  over expressions
      | { "not":   expr }
      | { "ref":   <namedConditionKey> }              // reference a named condition
      | { "some":  <repeatScope>, "where": expr }     // ∃ over repeat items
      | { "every": <repeatScope>, "where": expr }     // ∀ over repeat items
      | { "field": <path>, "op": <operator>, "value": <literal> }

operator := eq | neq | in | nin | contains | gt | gte | lt | lte | exists | empty | matches
```

`all` / `any` combine **expressions**. `some` / `every` quantify over **repeat items**. These are different operations and are deliberately named differently — conflating them is a permanent source of confusion.

**`in` vs `contains`.** `in` asks whether the answer is one of a list; `contains` asks whether an array-or-string answer includes a value. Kept distinct so neither operator's meaning depends on the shape of the answer it is applied to. `contains` also already exists in production's `StepCondition`, so it is required for round-tripping — it was missing from an earlier draft of this grammar, which would have made existing forms uncompilable.

### Addressing

Answers are keyed by **placement**, not by question key alone:

```
practiceLocation.line1        billingAddress.line1
```

A form composing the catalog's address questions into four sections (practice, billing, remit-to, mailing) produces four independent answers. Without placement scoping they are one slot and the later write destroys the earlier one — a wrong answer, not an awkward one. See §5.6.

**A rule inside a section names a sibling by bare key**, and the compiler qualifies it against the
step that placed the section:

```
authored on the section        compiled, placed as practiceLocation
{ "field": "line1", ... }  ->  { "field": "practiceLocation.line1", ... }
```

This is not a shorthand, it is the only correct form. A section is reusable and cannot know the step
key it will be placed under — that is chosen at placement time, and the same section may be placed
twice. A rule that hardcodes `practiceLocation.line1` compiles clean and gates *both* copies on the
practice location's answer, so the billing address's field appears because of something typed in a
different section. The compiler now refuses that (`CROSS_PLACEMENT_REFERENCE`) and raises a notice
for the milder case of a rule naming its own current placement, which works but stops the section
being reusable.

A **dotted** path in a question rule therefore means a genuine cross-section reference — a question
in Licensure gated on an answer in Applicant Details — which is legitimate and common. Context paths
(`viewer.role`) and `@item.` paths are left alone, having no placement to belong to.

> This paragraph did not exist, and its absence was the root cause of a real defect. The section
> aggregate and its unit tests were written for bare keys; the compiler's scope was keyed only by
> qualified paths, so a bare key failed as `DANGLING_PATH`; the fixtures were then written qualified
> to satisfy the compiler. Two halves of one feature, each guessing, and no test spanning both. The
> specification owed them an answer and did not give one.

Inside a repeating scope, `@item.` addresses the current repetition:

```json
{ "some": "licensure", "where": {
    "field": "@item.licenseExpiration", "op": "lt", "value": "+90d" } }
```

Rules of the form *"if **any** license expires within 90 days"* are common in credentialing and are unrepresentable without a quantifier.

A bare path nested inside a `some`/`every` still qualifies to the step that placed the section, not to
the repetition — `@item.` is how a repetition is addressed. That is a choice rather than a
consequence, so it is stated rather than left to be discovered.

### Named conditions

The same rule gates several places. A specialty exemption will gate DEA registration, controlled substances and prescribing privileges. Three inline copies drift.

Named conditions live on the form definition and are referenced as a single row:

```json
"namedConditions": {
  "specialtyExempt": {
    "label": "Specialty exempt from DEA requirements",
    "expr": { "field": "applicantDetails.specialty", "op": "in",
              "value": ["DC", "OD", "PhD", "Pathologist", "Radiologist"] }
  }
}
```

```json
"visibleWhen": { "not": { "ref": "specialtyExempt" } }
```

This gives composition without nesting — the answer to "what happens when a flat list isn't enough" that does not put parentheses in an ops person's head. Named conditions are resolved and **inlined at compile**, consistent with P3: editing one changes nothing already published.

### Option filtering — sugar, not a second mechanism

Filtering an option list is the same grammar attached to an option value:

```json
{ "value": "cardiology", "label": "Cardiology",
  "optionWhen": { "field": "applicantDetails.providerType", "op": "in", "value": ["MD", "DO"] } }
```

Value **tags** remain as an authoring shorthand for the common set-membership case, because they are far more compact across a 200-value specialty set — but they **compile to `optionWhen`**. One mechanism underneath, two ways to author it. A tag is never a parallel evaluator.

### Authoring semantics

Two rules that belong to the grammar's presentation, not to a screen:

**No exposed negation.** A `Show`/`Hide` verb crossed with `all`/`any` covers all four De Morgan combinations without ever showing the author a NOT:

| Verb | Combinator | Compiles to |
|---|---|---|
| Show | all | `{all: [...]}` |
| Show | any | `{any: [...]}` |
| Hide | all | `{not: {all: [...]}}` |
| Hide | any | `{not: {any: [...]}}` |

An invert checkbox over a multi-row group is De Morgan as a control: *"show unless A and B"* reads as "hide if either" and means "hide only if both". `Hide when specialty is any of …` matches how the policy is actually spoken.

**Prose resolves through the option set.** A summary must print option **labels**, never stored values. `DC` is a value in both the provider-type and specialty sets with different meanings, so raw values are ambiguous. This makes the option set part of a condition's *meaning*, not just its input widget — the compiled artifact must carry enough option data for the renderer to render prose.

### Where it runs

| Concern | v0 | Later |
|---|---|---|
| Parse + static validation (cycles, dangling refs, unreachable, unresolved `ref`) | **Backend, at compile** | — |
| Runtime evaluation for rendering | Frontend | Frontend |
| Runtime evaluation as authority (validation, requiredness, hard stops) | — | Backend |

Client-only enforcement is advisory. Server-side evaluation is required eventually, but the frontend implementation must remain for instant reveal — so **the conformance suite is the contract between the two implementations**.

## 7. Lifecycle & Versioning

### Authoring → publish

```
  section_templates ──copy──▶ section_definitions ─┐
  form_blueprints   ──copy──▶ form_definitions ────┼──▶ compile ──▶ form_versions
  question_catalog  ──ref───────────────────────────┘                (immutable)
```

`FormCompiler` is a pure function over `(definition, catalogSnapshot)`. It:

1. Resolves catalog references and applies instance overrides
2. Drops `enabled: false` questions and sections entirely
3. Validates: unique instance keys, resolvable external refs, no cycles, no unreachable sections, no condition literal outside its option set
4. Emits the compiled artifact in the **existing** runtime format

Failure produces a structured `CompilationReport`, surfaced as a machine-readable `422` the authoring UI can render inline.

### Change classification

| Class | Definition | Effect on in-progress work |
|---|---|---|
| `text` | Labels, help text, intros only | None |
| `additive` | New optional questions/sections only | None |
| `structural` | Anything else | Reset answers for `changedKeys` only |

Derived from a diff of the two compiled artifacts. This retires a human-ticked checkbox that currently decides whether providers lose their work.

`PreviewChangeSet` runs compile + diff **without persisting**, so an author sees *"structural — 12 in-progress applications will lose answers to 3 questions"* before publishing. Free once the compiler exists.

### Active version is derived, not flagged

Rather than mutating the previous version to `status: inactive`, **active = the highest version with `publishedAt` set.**

- One insert per publish, no multi-document write, no transaction
- Version records become genuinely immutable — required for "reproduce exactly what the provider signed"

### Event

```java
FormVersionPublished { formVersionId, formId, changeClass, changedKeys }
```

Emitted by `form_authoring`. In v0 there is no subscriber. When `form_response` arrives, it owns what "reset" means — `Application.rebaseTo(versionId, changedKeys)` lives inside the aggregate that owns the answers.

## 8. Service Architecture

### 8.1 Layering rule

The application layer **orchestrates**; it holds no business rules. Load aggregate → call domain → persist → emit event. If a method contains an `if` a credentialing analyst would recognise as policy, it is in the wrong layer.

Dependencies point inward only: `interfaces → application → domain`, and `infrastructure → domain` (it implements the ports). **Domain imports nothing from the other three.** One ArchUnit test enforces this, plus a rule forbidding cross-context imports except through published ports.

### 8.3 Quarkus decisions

**Virtual threads, not Mutiny.** The existing service is `Uni<>` chains nested four deep. `@RunOnVirtualThread` with blocking Mongo calls gives imperative domain code that reads like the rules it encodes. There is precedent — the submission pipeline already runs on `newVirtualThreadPerTaskExecutor`.

**Document ≠ aggregate.** No Panache or BSON annotations on domain objects. Panache is used in `infrastructure` over separate `*Document` types with explicit mappers. This costs one mapper per aggregate and is the single thing that keeps the domain model honest — since the POC exists to *propose* this paradigm, leaking Mongo into the domain would undercut the argument.

**No `@Transactional`.** Aggregate boundary = document boundary = atomic write. §7 removes the only multi-document write.

**Reads bypass the domain.** CQRS-lite. Inventory, version history, catalog search, and usage queries hit Mongo directly and project into view records. Forcing every read through an aggregate is where DDD projects get slow and teams start resenting them.

### 8.4 Controller rules

| Rule | Why |
|---|---|
| One application-service call per endpoint | Two calls means a use case with no home |
| Never serialize a domain object | Aggregates are behavioural; views are wire shape |
| No `try/catch` | Domain exceptions map centrally |
| DTOs use primitives; commands use value objects | The controller is the translation point — that is its job |
| No `@Transactional` | See above |

### 8.5 Application service

```java
@ApplicationScoped
public class PublishFormVersionHandler {

    @RunOnVirtualThread
    public PublishedVersionView handle(PublishFormVersion command) {

        FormDefinition definition = definitions.require(command.definitionId());

        CatalogSnapshot snapshot = catalog.resolve(
                definition.referencedQuestionIds(),
                definition.referencedOptionSetKeys());

        CompiledForm compiled = compiler.compile(definition, snapshot);

        ChangeSet change = ChangeSet.between(
                versions.findActive(definition.formId()).orElse(null),
                compiled);

        FormVersion published = FormVersion.publish(
                definition, compiled, change, command.requestedBy());

        versions.save(published);

        events.publish(new FormVersionPublished(
                published.id(), definition.formId(),
                change.changeClass(), change.changedKeys()));

        return PublishedVersionView.of(published);
    }
}
```

Zero policy. `compile`, `ChangeSet.between`, and `FormVersion.publish` are all domain.

### 8.6 Exception mapping

```java
public sealed interface DomainException
    permits NotFound, InvariantViolated, CompilationFailed, ConflictingState {}

@Provider
public class DomainExceptionMapper implements ExceptionMapper<DomainException> {
    @Override
    public Response toResponse(DomainException e) {
        return switch (e) {
            case NotFound n          -> problem(404, n.message());
            case ConflictingState c  -> problem(409, c.message());
            case InvariantViolated i -> problem(422, i.message());
            case CompilationFailed f -> problem(422, f.message(), f.report());
        };
    }
}
```

A sealed hierarchy gives an exhaustive switch — adding a domain exception without handling it will not compile. This replaces the `ErrorHandlerUtil.handleDalError(e, "Failed to …")` line repeated in every method of every existing resource.

## 9. API Surface (v0)

> **As built.** The list below is what the POC actually exposes, corrected against the code. Two
> things changed from the original plan. Placements are `/steps` rather than `/placements`, matching
> the vocabulary the rest of the model settled on. And the assembly verbs — place, remove, reorder,
> the named-condition writes, and both promote-upward paths — were **missing from the first cut and
> added afterwards**; see the note at the end of this section, because how they went missing is more
> interesting than the endpoints.

### `question_catalog`

```
GET    /api/v1/tenants/{tenantId}/catalog/categories                  the taxonomy, in order, with counts
GET    /api/v1/tenants/{tenantId}/catalog/questions                   search; includeProposed opts in
GET    /api/v1/tenants/{tenantId}/catalog/questions/{questionId}
POST   /api/v1/tenants/{tenantId}/catalog/questions/{id}/promote      proposed → active, dedupe-checked
POST   /api/v1/tenants/{tenantId}/catalog/questions/{id}/aliases      absorb a payer's phrasing
POST   /api/v1/tenants/{tenantId}/catalog/questions/{id}/deprecate
GET    /api/v1/tenants/{tenantId}/catalog/option-sets
```

Corrected against the code, which found three endpoints this document claimed and the service does
not have: `POST /questions` (propose), `PUT /option-sets/{key}`, and `GET /questions/{id}/usage`.
Nothing depended on them — proposed questions arrive through the fixtures, and usage is answered by
`form_question_usage` at compile time rather than over HTTP — but a design document that lists
endpoints nobody built is the same failure as a fixture standing in for a workflow, one layer up.
All routes are tenant-scoped, which the original list also had wrong.

### `form_authoring` — sections

```
GET    /api/v1/tenants/{tenantId}/sections
POST   /api/v1/tenants/{tenantId}/sections                        from template, or blank
GET    /api/v1/tenants/{tenantId}/sections/{sectionId}
POST   /api/v1/tenants/{tenantId}/sections/{sectionId}/questions   add from the catalog
PATCH  /api/v1/tenants/{tenantId}/sections/{sectionId}/questions/{key}   enable/disable
PUT    /api/v1/tenants/{tenantId}/sections/{sectionId}/questions/order   whole key list
GET    /api/v1/tenants/{tenantId}/sections/{sectionId}/drift
POST   /api/v1/tenants/{tenantId}/sections/{sectionId}/promote?key=      → template
```

`DELETE .../questions/{key}` is listed in no version of this document any more: it is deliberately
not implemented. Disabling compiles a question out of the artifact entirely — the same runtime effect
— while keeping the provenance a template upgrade reconciles against. It would be the one operation
in this API that destroys information a later reconciliation depends on.

`promote` covers both directions of the reuse loop, because from the author's side it is one
intention and which applies is a fact about the section: template-backed sections get version n+1,
from-scratch sections get a brand-new template at version 1, which is what `key` names. The new
template is **tenant-owned, not global** — publishing one client's section shape to every tenant is a
curation decision, not a side effect of pressing a button.

### `form_authoring` — forms

```
GET    /api/v1/tenants/{tenantId}/forms
POST   /api/v1/tenants/{tenantId}/forms                  from blueprint, or blank
GET    /api/v1/tenants/{tenantId}/forms/{formId}
POST   /api/v1/tenants/{tenantId}/forms/{formId}/steps               place a section
DELETE /api/v1/tenants/{tenantId}/forms/{formId}/steps/{stepKey}
PUT    /api/v1/tenants/{tenantId}/forms/{formId}/steps/order         whole key list
PATCH  /api/v1/tenants/{tenantId}/forms/{formId}/steps/{stepKey}/condition
PUT    /api/v1/tenants/{tenantId}/forms/{formId}/conditions/{key}    upsert a named condition
DELETE /api/v1/tenants/{tenantId}/forms/{formId}/conditions/{key}    409 while referenced
GET    /api/v1/tenants/{tenantId}/forms/{formId}/validate            compile, do not persist
GET    /api/v1/tenants/{tenantId}/forms/{formId}/change-preview
POST   /api/v1/tenants/{tenantId}/forms/{formId}/publish
POST   /api/v1/tenants/{tenantId}/forms/{formId}/promote              → blueprint
GET    /api/v1/tenants/{tenantId}/forms/{formId}/versions
GET    /api/v1/tenants/{tenantId}/forms/{formId}/versions/{versionId}/compiled
```

`DELETE /steps/{stepKey}` is a real delete, in contrast to a section's questions. The asymmetry is
deliberate: a question's origin is provenance, while the section a step placed still exists and can
be placed again, so there is nothing to preserve by keeping a husk.

Both reorder endpoints take the **whole key list**, never one item and a position. A partial reorder
cannot be made safe — an omitted key keeps its old number, two can end up sharing one, and the sort
then decides the sequence a provider sees rather than anything the author wrote.

Every mutating form endpoint refuses a published definition with a 409. A published definition is the
record of what was published; editing it would rewrite history for providers mid-application.

### Rules — a read model

```
GET    /api/v1/tenants/{tenantId}/rules      every condition, with what it reads
```

Derived on every call and stored nowhere. An index of rules that could disagree with the rules is
worse than no index, because an author would trust it.

Server-side rather than assembled in the browser, and the reason is not round trips. Deriving it in
the client would mean fetching every form and section and then reimplementing ref resolution and path
collection in TypeScript — a second `ExpressionAnalyzer` whose only consumer is one read screen. The
conformance suite exists to keep the two *evaluators* in step; it says nothing about a bespoke
analyzer written for a view.

Three things it reports that nothing else could answer:

- **`reads` resolves through refs.** A step gated entirely by a named condition depends on whatever
  that condition reads. Stopping at the ref would report it as depending on nothing, and the reverse
  index — "what breaks if I change this question" — would be useless exactly where it matters most.
- **Unconditioned steps are listed**, with a null rule rather than being filtered out. The most
  consequential fact about a rule set is often the rule that is absent: three Florida Blue sections
  ship unconditioned in production, a defect indistinguishable from a working form.
- **Operator usage counts rules, not occurrences.** The question it answers is what a migration has to
  support, and the answer is reliably a fraction of the grammar. On the seeded tenant: four of twelve.

It also returns a path-to-label map, resolved from the catalog in one batched read, so a rule renders
as *"Show when Do you have a CAQH ID? is Yes and Is the billing address the same as your primary
practice address? is No"* rather than as two answer paths. That is not decoration on a screen whose
entire purpose is inspection — a rule an author cannot read is a rule they will not check. A label
override beats the catalog label, because an override exists precisely where a payer words the
question differently, and a missing catalog entry falls back to the raw path rather than guessing.

### Blueprints and templates

```
GET    /api/v1/tenants/{tenantId}/section-templates
GET    /api/v1/tenants/{tenantId}/section-templates/{templateId}
GET    /api/v1/tenants/{tenantId}/blueprints
GET    /api/v1/tenants/{tenantId}/blueprints/{blueprintId}
```

Read-only, and tenant-scoped even though most entries are global — the reads return global entries
plus that tenant's own, and one tenant must not be able to enumerate another's. There is no `POST`:
a reusable shape is not authored directly, it is **promoted** from something a tenant actually built
and evolved, which keeps shared shapes grounded in real use rather than in a guess about what will
turn out to be reusable.

### How the assembly verbs went missing

Worth recording, because the failure mode generalises.

The first cut of this API had five write commands: create-a-form-from-a-blueprint,
create-a-section-from-a-template, update-a-step's-condition, preview and publish. Reads were
complete. The editing loop worked, CP-38192's rule change worked, and the demo walked end to end.

What did not exist was `POST /steps`. Every form therefore had to be instantiated from a blueprint,
and every blueprint was a JSON fixture written by hand — so a payer nobody had onboarded before could
not be started at all, and the studio had no screen for it either.

Nothing failed, because the seed data stood in for the missing verb: a form was always already there
to edit. The domain was never the gap — `FormDefinition.placeStep`, `removeStep` and
`withNamedCondition` existed from the first week, reachable only from the blueprint path and from unit
tests. The absence was entirely in the application, REST and UI layers, and no test asked for it.

Two things fell out of fixing it that are properly design changes rather than plumbing:

1. **`BlueprintPlacement` gained `visibleWhen`, and `FormBlueprint` gained `namedConditions`.**
   Without them, promoting a form to a blueprint and instantiating it produced a form with every
   condition stripped — structurally identical, logically empty. That is the same class of defect as
   the three Florida Blue sections that ship unconditioned today, and it would have looked like a
   success because the form still renders. `MongoCodecRoundTripTest` now covers a placement carrying
   a `ref` and the blueprint carrying its definition, because each is useless without the other.
2. **Command guards throw `InvariantViolated`, not `IllegalArgumentException`.** A command is
   constructed from a request body, so its guards validate caller input and must answer 422.
   `IllegalArgumentException` has no mapper — by design, since it means an aggregate refused and a
   service is expected to translate — so a command throwing one reached the client as an opaque 500
   for a request the client could have fixed. Bean validation cannot cover these cases: both create
   commands are legal with different required fields depending on whether a blueprint or template was
   named, and `@NotBlank` has no way to say "required only when that other field is absent".

## 10. Success Criteria

Ordered by how much each would change the decision.

**1. Round-trip — the primary gate.** *(deferred — see §11, seed importer)*
Recompile the three existing form schemas from definitions and diff the output against their currently published `schema`, using the canonicalisation rules below. A match proves the model is expressive enough, with no room for interpretation.

This gate depends on the **seed importer**, which is parked. Until it lands, the POC runs on hand-authored demo fixtures — which demonstrate the flow but do **not** validate expressiveness. Fixtures are unconsciously shaped to fit the model; only real forms test it.

**Canonicalisation rules — frozen before the test runs, so a failure cannot be argued away:**

| Aspect | Treatment |
|---|---|
| Object key order | Ignored |
| Array order (placements, questions, options) | **Significant** — order is meaning |
| `null` vs absent | Equivalent |
| `[]` vs absent | Equivalent |
| Whitespace, number formatting | Ignored |
| Everything else | Must match |

Implementation: canonicalise both sides (recursive key sort, drop nulls and empty arrays, normalise numbers), then compare exactly — semantic comparison with a readable diff on failure.

**Answer shape.** v0 compiles to the existing nested shape (`answers["Section Name"]["fieldKey"]`) so the diff is meaningful. The *target* is placement-scoped (`answers["billingAddress"]["line1"]`) — the same nesting, keyed by stable `placementKey` instead of display label. Note this is **not** the flat global namespace an earlier draft proposed: flat collides the moment two placements reuse one catalog question (§5.6).

**Grouping — resolved.** One level: a placement compiles 1:1 to a `step`. The earlier two-level design (pages → sections) is dropped; see §5.6. This unblocks the compiler and makes the diff structurally comparable by construction.

**2. CP-38192 as pure config.**
The NSCP form's four compound-AND sections (Billing Address, Additional Practice Location, Group Details, Contracting Details) and Florida Blue's three `in`-gated sections (Licensure, DEA Registration, Professional Liability Insurance) express correctly as configuration, with no per-form code.

~~with **zero rendering-engine changes**~~ — struck, because it is unachievable and this document said so in §3 P2 while still claiming it here. A recursive `all`/`any`/`not` cannot be represented in production's flat `{field, operator, value}` condition slot, and that recursion is the entire substance of CP-38192. The compiler emits the existing artifact *shape*; the condition slot is a genuine breaking change to the renderer. See the amendment under P2 for what that costs.

**3. Catalog collapse rate.**
Across the three existing forms, what fraction of questions resolve to shared catalog entries? This is the reuse thesis and it is a number. 80% and the catalog is transformative; 30% and it is much less compelling than it looks.

**4. Mapping derivation.**
Can one tenant's existing `fieldMappings` be regenerated purely from `platformMapping` plus exceptions? Count the exceptions.

**5. Change classification accuracy.**
Run the diff against a real published version pair and check whether it agrees with what a human ticked.

**6. A new payer form can be assembled from nothing.** *(added late — see the note at the end of §9)*
Starting from an empty tenant and a populated catalog, can an author create a form, build the
sections it needs, place them, write the rules and publish — with no fixture, blueprint or template
involved? This was not in the original criteria, which is why its absence went unnoticed for most of
the build: every other criterion could be met by editing a form the seed data had already created.

## 11. Out of Scope & Parked

### PDF ingestion — parked, design retained

Most payers already have a PDF form Certify digitises. The key reframe: **the AI's job is extraction and matching, not authoring.** With a catalog and blueprints in place, an open-ended generation problem becomes a bounded retrieval problem.

Five stages, with decreasing AI autonomy:

1. **Extract** — PDF → ordered raw items: label, help text, response-type guess, visible options, heading, page + bounding box. Mechanical, high accuracy.
2. **Match to catalog** — each item → candidate catalog questions with confidence. Retrieval, not generation.
3. **Recognise sections** — cluster items against `section_templates`.
4. **Recognise the form** — match overall shape against `form_blueprints.recognitionHints`.
5. **Emit a diff, not a form** — *"Practitioner Recredentialing blueprint, plus 5 new questions, 3 disabled, 2 reordered."* Reviewing a ten-item diff against a known baseline is a fundamentally different task from auditing 200 generated questions. **This is the strongest argument for blueprints existing at all.**

Unmatched items become `status: "proposed"` catalog entries requiring human promotion with a fuzzy dedupe check.

**Conditions get the least autonomy.** Logic in a PDF appears as *"If No, skip to Section 5"*, an arrow, or nothing at all. Extraction accuracy will be poor and errors are **silent** — a wrong condition means a section that never renders. Suggestions only, each with the source sentence quoted and the page cited, human confirms every one. The compiler's validation pass is the backstop.

Staging collection (`form_import_sessions`) holds the temporary definition, keeping `sourcePage` + `sourceBBox` on every item so the review UI can show the original PDF region beside each proposed question. Without that provenance, reviewing a 200-question import is unbearable and people rubber-stamp it.

**Sequencing note:** build ingestion *after* the round-trip test passes. If the compiler cannot round-trip existing forms, the ingestion pipeline has nothing valid to target — building the expensive half first would be a mistake. The schema already accommodates it (`aliases`, `proposed` status, `recognitionHints`), so nothing needs migrating.

### Transformer — out of scope

Previously called the "seed importer"; **transformer** is the better name and the one to use. The
inverse of the compiler: reads an existing `form_versions.schema` and emits catalog questions, option
sets, section definitions, and form definitions. Required to run §10 criterion 1 mechanically
(`transform → compile → diff against original`).

Parked because it depends on the collections, the compiler, and the catalog all existing first. Two notes for when it is picked up:

- **Build it as a transformer, not by hand-authoring YAML.** It is a dry run for ingestion stage 2 — the label normalisation, alias matching, and dedupe logic is the same, but on structured JSON rather than OCR output, so it is deterministic and needs no AI. It also yields §10 criterion 3 (catalog collapse rate) for free, since it must decide new-vs-existing on every field.
- **Guard against a shared blind spot.** If the importer and compiler drop the same key, the diff passes while both are wrong. Always diff against the *original stored schema*, never the importer's intermediate, and assert **key coverage**: every key in the source must be mapped or on an explicit ignore list, with anything unaccounted-for failing loudly.

In the interim the POC runs on hand-authored demo fixtures (~30–40 catalog questions, a few option sets, 6–8 section templates, one blueprint, one form definition). Fixture *content* should be drawn from the real Florida Blue Recred form so it is grounded in reality even though the transformation is manual.

**The expressiveness question has since been answered without it.** Two real payer configs (Premera,
Highmark) were audited against the model by inspection — see
[`form-config-poc-expressiveness-audit.md`](./form-config-poc-expressiveness-audit.md). Of 99 fields
and 16 conditions, exactly three constructs are not expressible, only one of which changes the model
(answer keys are flat and global in production, so `QuestionInstance` needs an explicit answer-key
override). The audit also measures the normalisation payoff on real data — 18 inline option lists
collapsing to 3 — and records that cross-form question reuse is far lower than this design assumed:
2 shared field names out of ~99, which reframes the catalog's value as aliasing and duplicate
prevention rather than composition.

The measuring instrument for the mechanical version is already built: `ArtifactComparison` in test
support, with 16 calibration tests verified to fail on both too-strict and too-lax comparisons. When
the transformer is picked up, the gate is `transform → compile → compare`.

### Also deferred

| Item | Note |
|---|---|
| Response capture | `form_response` context; `FormVersionPublished` has no subscriber in v0 |
| Runtime expression evaluation | Frontend today; backend authority later |
| Server-side validation & hard-stop authority | Real correctness gap, tracked separately |
| Submission integration | Unchanged; consumes `platformMapping` later |
| Placement-scoped answer keys in the artifact | The model is placement-scoped from day one (§5.6); migrating the *compiled* shape from display-label nesting to `placementKey` nesting is a follow-on, after round-trip passes |
| Authoring UI | Definitions authored as YAML in a repo for v0 |

| Dependency / impact view | "What depends on this question." The data exists (`form_question_usage`, §5.8) and the diagram computes the edges, but no screen owns it. At 200 questions this is the view that decides whether anyone dares change anything |

## 12. Next iteration — bringing existing forms in

Scoped, not parked. §11 lists work with no committed shape; this is the one piece with a known shape,
a known trigger and a known cost, deferred only because its two halves have to land together.

### The pairing

The **transformer** (§11) converts an existing `form_versions.schema` into the authoring model. It
cannot land usefully without the **answer-key override**, and the override is dead weight without it.

The override is the finding from
[`form-config-poc-expressiveness-audit.md`](./form-config-poc-expressiveness-audit.md) §1.1, and it is
the only audit finding that changes the model rather than the compiler.

### Why the override is needed

This model derives a question's answer key from where it sits — `stepKey.questionKey`, so
`applicantDetails.npi`. Production uses a single flat global namespace: `npi`, `homeState`,
`attestationDate`.

Both are correct for their own purpose, and that is the whole difficulty:

- **Placement-scoping is right for new forms.** Florida Blue places one address section twice, and
  `practiceLocation.line1` must not collide with `billingAddress.line1`. A flat namespace cannot
  express that at all — it is the design review's central finding (Appendix A, finding 6).
- **Flat keys are right for existing forms**, because that is what their answers are already filed
  against.

Transforming Premera without the override renames all 57 of its answer keys. Every in-flight
application's answers orphan, silently, with nothing to error on — the same category of harm as the
destructive publishing this design exists to remove.

### Shape

One nullable field on `QuestionInstance`:

```
answerKey = null    → derive stepKey.questionKey    (anything authored fresh)
answerKey = "npi"   → use verbatim                  (set once, at transform time)
```

Set by the transformer, never edited afterwards. New forms never populate it and keep placement
scoping unchanged.

**It touches three places, not one**, and the other two are easy to miss:

| Where | Change |
| --- | --- |
| `QuestionInstance` | the nullable field |
| `FormCompiler` | emit the effective key — override if present, else derived |
| `ExpressionAnalyzer` scope | build from effective keys, or every transformed condition looks dangling |

That third one is the trap. A transformed form's conditions are flat — `{"field": "mailingSameAsPrimary"}`
— so an analyzer still scoped on derived paths would reject a form that is perfectly valid.

### Why it is not built now

Nothing can populate the field without the transformer. An override that nothing ever sets implies a
capability the system does not have — precisely the failure mode that made `sourceTemplateId` a
dangling pointer for most of this POC's life, where the model carried the reference, persisted it and
served it over the API while no template existed anywhere.

### Definition of done

- A real payer config transforms, compiles, and `ArtifactComparison` reports equivalence against the
  original stored schema. The comparator is built and calibrated (16 tests, verified to fail on both
  too-strict and too-lax comparisons), so the result means something.
- Transformed answer keys are byte-identical to the original, asserted per key rather than in
  aggregate.
- A form authored fresh in the studio still gets placement-scoped keys, so the override cannot leak
  into the default path.
- Key coverage is asserted: every key in the source schema is either mapped or on an explicit ignore
  list, with anything unaccounted-for failing loudly. §11 already names this as the guard against the
  transformer and compiler sharing a blind spot and agreeing on the wrong answer.

## 13. Risks & Open Questions

### Risk 1 — Catalog hygiene *(highest)*

Six months of auto-accepting proposed questions and the catalog holds "NPI", "NPI Number", "National Provider Identifier", and "Individual NPI" as four distinct entries. At that point reuse is zero and this is a worse version of what it replaced.

**This is the single biggest risk in the design, well ahead of anything technical.** Mitigations: `proposed → active` staging with human promotion; fuzzy dedupe against existing entries *and aliases* at promotion; aliases as the default landing place for payer-specific phrasing; a named steward.

### Risk 2 — Two expression implementations drift

Backend validates, frontend evaluates. Unavoidable — a round trip per keystroke breaks the instant-reveal UX in PRD §4.5. Mitigation: a shared conformance fixture set is the contract, and both implementations run it in CI.

### Risk 3 — DAL filter limitations

`formVersionFindMany` rejects `formTemplateId` and `status` as filter fields, which is why `PortalAdminService` fetches 500 versions unfiltered and groups in memory. New collections routed through the same DAL would inherit this.

**POC decision:** talk to Mongo directly from the POC service. Keeps v0 about validating the model rather than negotiating filter allowlists. Productionising the DAL surface is a later concern — and the DAL migration may remove it entirely.

### Risk 4 — Blast radius is a computation, not a number

"12 applications affected" is only truthful if it is *computed*: evaluate the previous and new compiled artifacts against each in-progress application's stored answers, diff the resulting visible-question sets, and intersect with `changedKeys`. Only applications the new rule actually hides lose that data.

Synchronous at a dozen applications; a background job at ten thousand. The capability is buildable, but success criterion 2 is only met by the real computation — a flat count is the demo version.

### Open questions

| # | Question | Resolution path |
|---|---|---|
| Q1 | Should section-level *and* placement-level question disabling both exist, or only section-level? | Start with section-level; add placement-level only if cross-form section sharing proves common |
| Q2 | Version numbering — keep the `×10` scaled encoding for compatibility, or plain integers with presentation formatting? | POC uses plain integers; compatibility shim at the boundary if needed |
| Q3 | Who is the catalog steward, and what is the promotion SLA? | Product/ops decision, needed before ingestion ships |
| Q4 | Is `(A AND B) OR C` nesting genuinely out of scope? CP-38192 flags it as unconfirmed | The recursive grammar supports it for free; confirm whether the frontend evaluator will |
| Q5 | Does the round-trip test need byte-for-byte equality, or semantic equivalence? | Semantic — canonicalisation rules frozen in §10 |
| ~~Q6~~ | ~~Pages vs steps~~ | **Resolved: placements are steps.** Pages dropped; `group` survives as a presentational label that compiles to nothing. See §5.6 |
| Q7 | Should catalog questions carry an `isDriver` flag? Real forms have ~8 questions that gate things and ~190 that are data. Marking drivers shrinks the dependency graph from 200×40 to 8×40 and defaults the condition field-picker sensibly | Recommend a declared flag plus a computed audit ("gates 3 sections but is not marked a driver"). Do not *restrict* which questions may gate — control questions like `hasCaqhId` blur the line |
| Q8 | Are named conditions live-referenced or frozen at compile? | Frozen, per P3 — inlined into the artifact. Editing one never changes a published version |

## Appendix A — Design review findings (applied)

A staff product designer reviewed the interactive prototype against the model. Verdict: **direction sound, proceed** — no "this is wrong in principle". Six findings were structural enough to change v0 while they were still free to change. Recorded here so the reasoning is not re-derived.

| # | Finding | Applied in |
|---|---|---|
| 1 | **Answers had no placement identity.** Two sections composing the same catalog address question shared one answer slot; the second write destroyed the first. Structural, not cosmetic — four addresses on a real form makes it certain | §5.6 `placementKey`, §6 Addressing, §10 |
| 2 | **No quantifier over repeat items.** *"If any license expires within 90 days"* was unrepresentable. `@item.` scoped within an item but nothing ranged across them | §6 `some` / `every` |
| 3 | **Conditions attached only to visibility, and a second mechanism already existed** (option filtering by tags). Requiredness, defaults and validation would each arrive bespoke — engineers and tickets again, by a different route | §3 P6, §6 attachment points, §5.4 |
| 4 | **Expressions assumed answers were the only input.** Production already gates steps by viewer role (`audience`), which is not an answer | §6 Evaluation context |
| 5 | **Repeated rules would be copied and drift.** One specialty exemption gates DEA, controlled substances and prescribing | §6 Named conditions |
| 6 | **Pages carry no behaviour, and production has one grouping level, not two.** A compiler blocker, not a layout preference | **Resolved** — placements are steps, §5.6 |

Three further findings were accepted as deferred work rather than model changes: no home for "what depends on this question", compilation surfaced as a mode rather than continuously, and Structure/Fill preview being peers when they are one activity. All are in §11.

Two authoring-semantics corrections are recorded in §6 rather than as UI notes, because they belong to the grammar's presentation and would otherwise be re-litigated per screen: **no exposed negation** (a `Show`/`Hide` verb replaces an invert checkbox, which is De Morgan as a control) and **prose resolves through the option set** (print labels, never stored values — `DC` means different things in two different sets).

The review also noted that `isDriver` would shrink the dependency graph from 200×40 to 8×40; captured as §13 Q7 rather than applied, since the driver/data boundary is fuzzier than it first appears.
